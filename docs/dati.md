# Data and updates

Where the data comes from, how it is organised, how it is updated and how the repository is laid out.

## Regions and data

The data comes from Overpass (`natural=tree` and `natural=tree_stump`) and is divided by region. On opening no region is loaded: the map shows the countries, coloured from green to red according to their position in the ranking by share of trees with errors (grey if the data or counts are missing). Countries divided into regions (Italy, Poland, France, Spain, United Kingdom, Ireland, Austria) have the national boundary: tapping them shows their regions, coloured in the ranking only among themselves. The others (Bulgaria, Latvia) load directly. A region can also be chosen from the menu, where regions are grouped by country. "← All countries" returns to the overview. Direct address: `#region=lombardia`. On opening the map frames the largest group of nearby regions (Europe); distant regions, such as Japan, Venezuela or Chile, are reached from the menu.

* `data/regions/<region>.geojson.gz` – the trees of a region, with the checks already computed (compressed: the browser decompresses them) and the day of the last edit of each node (`ts`, from the OSM metadata; user and changeset are not kept). The valid date of a single measurement, from `check_date:height=*`, `check_date:circumference=*`, `check_date:diameter=*` or `check_date:diameter_crown=*`, is in `md_<measurement>` ([issue #99](https://github.com/ivanbranco/tree-osm-qa/issues/99)): the page uses it in place of `ts` for the age of that measurement. Nodes with `xmas:feature=tree` that are not `natural=tree` or `natural=tree_stump` are downloaded too, but kept in a separate `xmas` list of the file, outside the trees, counts and checks: they are only drawn as Christmas trees from 8 December to 6 January. Tree rows (`natural=tree_row` ways) are downloaded in the same query; those with no tree or stump among their nodes go in a separate `rows` list of the file (way id, coordinates, `leaf_type` and `leaf_cycle` from the tags or estimated from the species), also outside the trees, counts and checks, only for [drawing](mappa.md#rendering) from zoom 16
* `data/regions/<region>.min.geojson.gz` – the reduced part of the same file: only trees with errors and monumental trees (`denotation=natural_monument` or `monument=tree`, and the members of [homogeneous groups](mappa.md#homogeneous-groups-of-the-masaf-list) of the MASAF list), the only ones visible below zoom 10. The site loads this first, which appears immediately, and meanwhile the full file, which for large regions (e.g. Lombardy, almost 400,000 trees) takes a few seconds; until it is ready the count says "loading all trees…". If the reduced file is missing, the site derives it from the full one
* `data/wikidata_items.json` – Wikidata cache of the items of `wikidata=*` (the individual trees): whether it is a taxon (has a scientific name, P225), coordinates (P625), image (P18), winter view (P5252, shown on the card in winter), species (P10241), protection (P1435), Wikipedia articles, monumentaltrees.com ID (P9704) and whether it is an instance of monumental plant (P31 = Q811534). At every update of a region the script re-reads all the QIDs that the region uses, so corrections made on Wikidata reach the checks; if Wikidata does not respond the cached data stays, and the Wikidata checks do not trigger for QIDs never verified
* `data/wikidata_taxa.json` – Wikidata cache of species and genera (from `species:wikidata`, `genus:wikidata`, P10241 and, for the `species` values present in the data, the wiki list): whether it is a taxon, scientific name (P225), rank (P105), labels and aliases in Italian and English (for the common name); updated in the same way, except that a QID is requested only once per run (regions updated together share most species) and the aliases only once per species; the items of the `species:wikipedia` articles are also there
* `data/wikidata_redirects.json` – QIDs of `wikidata` and of the `*:wikidata` keys of the trees that on Wikidata are a redirect (with the target QID) or a deleted item (`null`); only these QIDs are stored. Read again at every update, once per run
* `data/wikipedia_qids.json` – cache of the `species:wikipedia` articles (`language:Title`) with the QID of the linked Wikidata item, requested from the Wikipedia API of that language following redirects (`null` if the article does not exist or has no item), for the hints on `species:wikidata` and `species`; re-read at every update, each article once per run
* `data/fotoshi.json` – author and licence of Fotoshi photos (`image:fotoshi`), read from each photo's page only once
* `data/gphotos.json` – address of the photo of Google Photos links in `image` (`photos.app.goo.gl`, `photos.google.com`), read from the shared page (`og:image`, on lh3.googleusercontent.com) because the site cannot read it from the browser; reread every 30 days. An empty address means that the page gives no photo (for example a share that was removed). Each page is about 1.2 MB, downloaded during the update and not saved
* `data/inaturalist.json` – iNaturalist observations of the trees ([issue #104](https://github.com/ivanbranco/tree-osm-qa/issues/104)), from the iNaturalist API (v2, only the fields needed): for each observation the kingdom of the taxon and the first photo with an open licence (CC0, CC BY, CC BY-SA) and the first one with another Creative Commons licence, with author and licence; and the nodes linked to observations with the "OpenStreetMap (OSM)" observation field (`https://www.openstreetmap.org/node/<id>`). The observations with the field are all searched once per run (about 3,500, 18 requests), the others, from `ref:inaturalist.org`, when they are missing or were read more than 30 days ago. If iNaturalist does not respond, the data of the last search stays
* `data/url_status.json` – status of the links and Commons files already checked, with the date of the check
* `data/index.json` – list of available regions, number of trees, number of trees with errors (`errors`), date of the latest data change (`updated`), date of the OSM data of the latest download (`osm_base`, from `osm3s.timestamp_osm_base` of the Overpass answer; for a region downloaded in tiles, the oldest tile) and date of the latest download attempt, successful or not (`tried`, for `oldest`). The public Overpass servers are not all updated at the same moment: if an answer has OSM data older than `osm_base`, the previous data of the region is kept, and the Action gives a warning; it also warns when the tiles of a region have OSM data more than 6 hours apart (`BASE_SPREAD_MAX` in `scripts/fetch_trees.py`)
* `data/history.json` – history for the Trends tab (errors and number of trees) and for the ranking movements: for each region, rows `[date, trees, trees with errors]`, one per day (if a region is updated more than once on the same day the last value stays, so the last row always matches `data/index.json`). It is written by `fetch_trees.py` at every update, even when the data does not change; dates up to 10/11/2026 were reconstructed from earlier versions of `data/index.json`
* `data/records.json` – for the Record trees tab when no region is loaded: for each region and for each of the eight records (`height`, `trunk`, `slender`, `stocky`, `crown`, `oldest`, `elevation`, `isolated`; `elevation` only in the regions with elevations, and its trees have `elev`), the top ten trees of the region (`t` = the first 10 in list order, each with the tags the row needs, the error codes, the trunk drawn on the map `tr`/`tr_est`, `leaf_type` and the estimated `lt` for the crown outline in the comparison from above, and the position `c`; `m` = how many more trees are tied with the last one). The site merges the lists of the regions of the open level. It is written by `fetch_trees.py` at every update of a region, even when the data does not change; the rules are in `record_values` and `record_order`, see [Record trees](pannello.md#record-trees). `isolated` is computed with QLever (see [Most isolated](#most-isolated)) and the site always reads it from this file, also with a region loaded; its trees also have `iso` (km), `nk` (what is nearest: `tree`, `wood`, `forest`, `tree_row`) and `ni` (that OSM element, e.g. `way/123`), or `cap` when nothing is within 50 km; next to `t` and `m`, `d` is the day it was computed. A region not updated since the top ten was added still has the earlier form (`n` = trees tied at the first position, `t` = the first 10 of them, no `m`): the site recognises it and says that the list of that region is not complete yet
* `scripts/year_events.json` – the "what happened that year" sentences of the Oldest record: one entry per year, decade (`1850s`), century (`C16`) or year BC (`480 BC`), with the sentence in Italian (`it`) and English (`en`) and the title of the Wikipedia article used as source (`wiki_en`, and `wiki_it` when the Italian article exists). Written by hand, sorted from the oldest. A year without an entry uses the entry of its decade, if there is one (`975 BC` → `970s BC`, `1853` → `1850s`). A key preceded by an ISO code is an entry for the trees of that country (`JP:1159`, `JP:1150s`) or region (`IT-21:C16`) only, as in the `iso` of the regions in `scripts/regions.json`, used before the entry for every country; the order is: the region's year, the country's year, the year, then the same for the decade (or century). At the end of every "Update tree data" run the summary of the Action (and the log) lists the entries that are missing (years with neither their own entry nor one for their decade), each with the regions it comes from in brackets: the years of the dates in the top ten of Oldest of any region in `data/records.json`, not only of the regions updated by that run. The top ten of a country or of all regions is always inside the top tens of the regions, so the list covers every level of the site; the monumental trees map shows the button only for years that already have an entry
* `scripts/regions.json` – regions: name, English name (`name_en`, used when the site is in English), `group` (with `group_en`) (e.g. "Italia": regions with the same group appear together in the menu) and `group_rel` (the OSM relation of the country, for the national boundary on the map), ISO 3166-2 code (if it exists: the regions of England do not have one), `partial` (`true` for the regions of a country covered only in part, such as the United States: there the invitation to request a region shows the name of the state, see [The map](mappa.md#filters-and-regions)), OSM relation id (`rel`), approximate bbox and, if needed, `split` (initial tile subdivision levels: 0 for countries with few trees) and `seasons` (the region's own calendar of the [seasons](mappa.md#rendering), read by the page: first and last month of each phase, e.g. `{"leaves": [3, 10], "autumn": [11, 11], "bare": [12, 2]}` for the northern hemisphere; a month in no phase counts as leaves. No region has one for now) and `elevation` (an object with `high_species`, the species listed by the [hint](check.md#hints) on trees without `species` above 1800 m, as `{"needleleaved": [...], "broadleaved": [...]}`; for now only Piedmont. The elevations of the trees do not depend on it, see [Elevation](#elevation))
* `data/regions_boundaries.geojson` – simplified boundaries of the regions and of the countries divided into regions, to choose them on the map; generated by the "Update region boundaries" Action (from Nominatim). The Action downloads only the boundaries missing from the file (new regions or countries); tick "Download all the boundaries again" to replace them all, for example after a boundary or a `rel` in `regions.json` has changed (locally: `python scripts/update_boundaries.py --all`)
* `data/uncovered_boundaries.geojson` – boundaries of the areas not covered: the countries of `scripts/countries.json` without regions in `regions.json` and, in the countries covered only in part (`partial`), the states and territories (`parent`) without a region, shown only when the country is opened. On the map they are grey like the regions without data, and a click shows the invitation to request them (see [The map](mappa.md#filters-and-regions)). Written by the same Action, more simplified than the regions (0.05°, less for small polygons, so that microstates and islands do not disappear, and less again where the simplified outline would touch or cross itself, which in MapLibre hides everything in the same tile): about 145 KB compressed. On the page they are a layer of their own with a fixed grey, under the regions. An area that lies inside a larger one (Åland in Finland, Hong Kong and Macau in China) is left out, so that it is not drawn twice; the areas are sorted from the largest to the smallest, so one that overlaps a larger one only in part (Western Sahara and Morocco) is drawn on top and gets the click. A country or state leaves the file at the first run after its region is added to `regions.json`
* `scripts/countries.json` – the countries and territories with their own ISO 3166-1 code (French Guiana, Western Sahara…) and the states of the United States (ISO 3166-2 code, `parent`) that can appear as areas not covered, with OSM relation, Italian and English name. A territory with both codes (Puerto Rico: `PR` and `US-PR`) gets as `parent` the country of the ISO 3166-2 code: when that country is covered only in part, the territory is treated like its states, because the OSM boundary of the United States already includes Puerto Rico, the US Virgin Islands, Guam, American Samoa and the Northern Mariana Islands. Only administrative or disputed boundaries (no continents, statistical or maritime areas); with more relations for the same code, the one with the lowest `admin_level`. Written by `python scripts/make_countries.py <file.json> [...]` from the raw JSON of this Overpass query (overpass turbo: Export → raw OSM data): `area(id:3600148838)->.us; ( relation["type"="boundary"]["ISO3166-1"]; relation["boundary"="administrative"]["admin_level"="4"]["ISO3166-2"~"^US-"](area.us); ); out tags;`

**Update**: from GitHub, Actions → "Update tree data" → Run workflow, choosing from the menu `all`, `oldest`, `three-oldest`, `all-but-recent`, a group (`italia`, `polonia`, `regno-unito`, `francia`, `spagna`, `irlanda`, `austria` = all the regions of the country that are in `regions.json`) or a single region. `oldest` updates the country (all its regions) or the region without a group that was downloaded least recently: the date of a region is that of its latest download, even when the data did not change (last row of `data/history.json`) or the download failed (`tried` in `data/index.json`), and the date of a country is that of its region downloaded least recently; with equal dates the order of `regions.json` applies. `three-oldest` does the same with the three countries or regions without a group downloaded least recently, one after the other. `all-but-recent` updates every region, in the order of `regions.json`, except those downloaded in the last 7 days, today included (with the same date as `oldest`, so a failed download counts too); it works region by region, so a country can be updated only in part. The log says which ones were chosen (or skipped). To update several regions together, write them instead in the text field below the menu, separated by spaces or commas (e.g. `liguria veneto lettonia`): if the field is filled in, the menu is ignored. There are no automatic runs: the update starts only manually. If the download of a region fails its previous data stays; if the data does not change, the files are not modified.

**Tests of the checks**: `scripts/test_checks.py` holds a table of made-up trees, each with its tags and the check codes it must get (at least one case for every check, cases for a correct tree, and cases where a check must stay silent because another one already reported the value). It runs the checks on all of them without using the network and, when a result differs, prints the case, the expected codes and the ones obtained; a check without any case is reported too. A few more cases cover the hint on the MASAF threshold and the [homogeneous groups](mappa.md#homogeneous-groups-of-the-masaf-list) of the MASAF list (reading made-up relations, and the members in the region data). The "Test checks" Action runs it at every push that changes `scripts/`, and "Update tree data" runs it before downloading: if it fails, the update does not start and nothing is published. The cases do not depend on the reference files (`whitelist.json`, `species_limits.json`, the wiki lists, the caches in `data/`): the test replaces them with small tables of its own. When a check is added or changed, the cases are updated with it. Locally: `python scripts/test_checks.py`.

Overpass server: the "overpass" menu of the "Update tree data" and "Update monumental map" Actions chooses the server with a key used first, before the public servers (overpass-api.de and the others in `ENDPOINTS`):

* `fairwaymapper` (default): the [FairwayMapper](https://www.fairwaymapper.com/api/overpass) mirror with the secret `FAIRWAYMAPPER_KEY` (address `https://api.fairwaymapper.com/k/<key>/api/interpreter`; the secret can contain just the `fm_…` key or the whole address used in overpass-turbo), at most 10 requests per minute;
* `overpass.ch`: [overpass.ch](https://overpass.ch/docs) with the secret `OVERPASS_CH_KEY`, the same one used for the [elevations](#elevation) (address `https://api.overpass.ch/v1/<key>/interpreter`), one request at a time (Overpass queries and elevations), at least 2.1 seconds apart. The longest query allowed depends on the plan of the key (3 minutes on Starter): a query that does not finish in time is split into more tiles;
* `public servers only`: no key is used, to save the quotas.

The secrets are in Settings → Secrets and variables → Actions, and the keys do not appear in the logs. If the key is rejected or the monthly limit is exhausted, the rest of the run uses only the public servers; with too many requests per minute it waits as long as the server says (up to two minutes) and tries again. Without the secret only the public servers are used. Locally the keys are passed with the environment variables of the same name; `OVERPASS_CH_KEY` alone is used only for the elevations, and overpass.ch is used for Overpass only with `OVERPASS_CH_OVERPASS=1` too (with both keys, overpass.ch comes first).

Locally: `python scripts/fetch_trees.py lombardia` (or `all`, `oldest`, `three-oldest`, `all-but-recent`, `italia`, `liguria veneto`). A new region is added to `scripts/regions.json` and to the menu of `.github/workflows/update.yml`; then run "Update region boundaries" and "Update tree data".

In the Italian regions the update also reads, with a separate Overpass query, the relations with `ref:masaf` that have at least one member in the region (tags and members), for the [homogeneous groups](mappa.md#homogeneous-groups-of-the-masaf-list) of the MASAF list. The `natural=tree` nodes that are members get the `mg` property: one row per relation, `id|removed|ref:masaf|masaf:criteria|name` (removed = 1 if the MASAF list gives at least one code of the relation as removed). If that query does not answer, the update goes on with a warning, keeping the groups of the previous update for the trees that are still there; the rest of the data is not affected.

Large regions are downloaded in pieces (tiles) and merged. The exact boundary is decided by the OSM administrative area; the bbox only serves to split the work, so if trees are missing at the edges of a region it is enough to enlarge it in `regions.json`.

### Elevation

The update adds to every tree and stump the `elev` property: the elevation above sea level in metres, to the decimetre, from the [Elevation API of overpass.ch](https://overpass.ch/docs) (`add_elevation` in `scripts/fetch_trees.py`). It is used by the [Highest elevation](pannello.md#record-trees) record and by the [hint](check.md#hints) on trees without `species` above 1800 m. Outside Switzerland and Liechtenstein the model is Copernicus GLO-30, a 30 m grid of the surface that includes canopies and buildings; in Switzerland swissALTI3D, the ground on a 2 m grid. The key is the secret `OVERPASS_CH_KEY` (Settings → Secrets and variables → Actions; locally the environment variable of the same name); it can contain just the key or the whole address used in overpass-turbo (`https://api.overpass.ch/v1/<key>/`). The key is in the request address, and it does not appear in the logs. The elevations are requested only when "elevation" is ticked when launching the Action (the default; locally: the environment variable `ELEVATION=1`), and only for the trees that have none: new or moved trees, or every tree of a region updated with the option for the first time (up to 10,000 points per request, one lookup per point, one request at a time, at least 2.1 seconds apart). The others are taken from the previous file of the region. Unticked, to save the quota of elevation lookups, no elevation is requested: the trees that already have one keep it, the others stay without. Without the key, or if the service does not answer, the trees without an elevation in the previous file stay without one and the update goes on with a warning; if the key is refused, no more elevations are requested for the rest of the update.

### Most isolated

The [Most isolated](pannello.md#record-trees) record needs the trees, woods and tree rows of the whole world, not only those of the region, so `fetch_trees.py` asks the public [QLever](https://qlever.dev/osm-planet) service (`osm-planet`, no key; `region_isolated`). This is done locally, not by the "Update tree data" Action, see below. It runs two queries. The first finds the 500 trees inside the region's OSM relation (`rel` in `regions.json`) that are farthest from their nearest tree. The second runs in groups of 50 of those trees and finds woods (`natural=wood`, `landuse=forest`) and tree rows (`natural=tree_row`) within the distance to the nearest tree of the first tree of the group, capped at 50 km. The isolation of a tree is the smaller of the two distances. The script stops when the tenth tree of the list is more isolated than the next candidate, so the top ten is exact. If the 500 candidates run out first, it asks for 2,000 and then 8,000. This happens in regions with many woods, where most of the trees far from other trees have a wood nearby: Lower Austria needs about 700. Only if 8,000 are not enough either does the log warn that the list may not be exact. Trees of the list with nothing within 50 km (remote islands) get one more query, with the radius extended to their nearest tree, to find the real distance; it is slow (about 2 minutes), and if it does not answer they show "over 50 km". Trees that are not in the region's data (QLever's copy of OSM can be a few days behind) and tree stumps are left out. A region takes about 15–35 seconds. If QLever does not answer (one more attempt after 30 s), the record computed before stays.

**From GitHub Actions QLever refuses the requests** (HTTP 403 since 16/11/2026, while it answers from a home computer). So "Update tree data" does not compute this record: it keeps the one already in `data/records.json`. The record is computed locally, from the region files already downloaded in `data/regions/`, without changing the other records:

* `python scripts/fetch_trees.py --isolated oldest`: the region whose Most isolated was computed least recently (regions without it first). The date is `d` in `data/records.json`
* `python scripts/fetch_trees.py --isolated vaticano bulgaria`: those regions (also a country, e.g. `austria`, or `all`)

Then `data/records.json` is committed and pushed as usual. Run the update of the region first and then the local command, otherwise the record may list trees that are no longer in the region's data.

The species pages (`species/`, made locally with `python scripts/build_species.py "Ginkgo biloba"`) have the same record, with the top five (`species_isolated`). The trees ranked are those of the species in the page: in the site's regions (inside their OSM relations) and the monumental trees outside the regions. They are found on QLever with the `species=*` values used by those trees. The distance is measured, as above, from trees of any species, woods and tree rows. If QLever does not answer, the list of the page made before stays; with `--keep-isolated` QLever is not asked at all (for when only the page template has changed). The command also rewrites `species/index.json`, read by the tree cards and by the list of the pages (`species/index.html`, not generated). Next to each page the command writes `species/<slug>.mon.json`, the monumental trees of the species on OSM worldwide: the page downloads it only when "Monumental trees" is switched on above its map. For the dioecious species with traits in `index.html` (`sexTraits`, `SEX_PHOTO`), the command copies those texts and photos into the page for its "Male and female" section: after changing them in `index.html`, the pages are made again. In the same way, the command copies into the page the sentences of `scripts/year_events.json` for the trees of Oldest ([Record trees](pannello.md)) and prints the years that have no entry, neither for the year nor for its decade: after adding them, the pages are made again (`--keep-isolated` is enough). Each page also has the tags for the preview on social networks (title, description and the photo at the top of the species' Wikipedia article, from Wikimedia Commons). If Wikipedia does not answer, the photo and the Wikipedia links of the page made before stay. The species name can be written with any capitalisation (`"quercus robur"`): the page takes the name as written in the wiki list. The trees with at least one warning, shown with their share at the top of the page, include stumps, as the total of trees does. Under the synonyms, the top of the page lists the subspecies, varieties and cultivars tagged on the trees of the species, with the number of trees: `taxon:subspecies`, `taxon:variety` (or `variety`) and `taxon:cultivar` (or `cultivar`). Quotation marks and the species name and rank written before the value are left out (`taxon:cultivar=Acer platanoides 'Globosum'` counts as `Globosum`), spellings that differ only in capitalisation count as one, and a subspecies is shown as the whole name with `subsp.` (`laricio` → `Pinus nigra subsp. laricio`). After 12 names the list gives how many more there are. Trees with the subspecies, variety or cultivar written in `species=*` (`Populus nigra 'Italica'`) are not in the page. The "Elevation" section of the page uses the `elev` of the trees in the region files ([Elevation](#elevation)): the command does not ask overpass.ch for anything, and the trees of regions without elevations are left out (stumps and monumental trees outside the regions too).

### Inside a building

The [Inside a building](check.md#other-tags) check needs the buildings around the trees, which the region update does not download. They are taken from [QLever](https://qlever.dev/osm-planet), locally like Most isolated, because QLever refuses the requests of the Actions (`region_buildings` in `scripts/fetch_trees.py`). One query per region: the `natural=tree` nodes inside the region's OSM relation that are at distance 0 from a building (way or relation with `building=*`, not `building=no`) inside the same relation, so buildings across the region's border are left out. For each tree the script computes the distance from the nearest edge of the building (inner rings included) and writes it to `data/buildings.json`: `{"<region>": {"d": day of the computation, "t": {"<node id>": [lon, lat, "way/…", building value, metres from the wall]}}}`. The trees closer than 1 m to the wall are in the file too: the threshold applies when the region is updated. Vienna takes about 80 seconds.

* `python scripts/fetch_trees.py --buildings oldest`: the region computed least recently (regions never computed first)
* `python scripts/fetch_trees.py --buildings vienna lombardia`: those regions (also a country, e.g. `austria`, or `all`)

Then `data/buildings.json` is committed and pushed. The reports reach the site with the next update of the region ("Update tree data"), which reads the file. If QLever does not answer for a region, its previous computation stays.

## World map of monumental trees

[`monumental-trees/`](https://ivanbranco.github.io/tree-osm-qa/monumental-trees/) is a map to share without the QA part, with all the monumental trees (`denotation=natural_monument`, or `monument=tree`, which counts the same) in the world and not only those in the tool's regions.

It also includes trees that are monumental according to other sources but do not have `denotation=natural_monument` on OSM ([issue #13](https://github.com/ivanbranco/tree-osm-qa/issues/13)): those that in the QA tool have the error on the monumental source (`ref:masaf`, `ref:rami`, monumentaltrees.com, `heritage:operator`, or the Wikidata item with P9704, instance of Q811534 or protection P1435). Trees with `monument=tree` are not among them, even with that error: they already come from the worldwide query ([issue #95](https://github.com/ivanbranco/tree-osm-qa/issues/95)). They are taken from the data of the QA tool's regions, so only in the covered regions, and are drawn like the other monumental trees; the card explains where the monumentality comes from in plain words ("Not marked as monumental on OSM, but it is according to MASAF and Wikidata"), with the tags involved in the pop-up on the ⓘ ("denotation=natural_monument is missing on OSM; sources: ref:masaf, wikidata=…"). In Italy it also includes the trees with the hint on the MASAF threshold (circumference at least equal to the MASAF indicative minimum circumference for the species, without `denotation=natural_monument` or `landmark` and without `ref:masaf`), except those with an error on the circumference: the card says "Not marked as monumental on OSM, but its circumference (4 m) reaches the minimum circumference set by MASAF for Wisteria sinensis (1.5 m)". Their number is in `implicit` in `data/world/index.json`; `masaf_size` counts those included only for the MASAF threshold.

It also includes, from the data of the Italian regions of the QA tool, the members of [homogeneous groups](mappa.md#homogeneous-groups-of-the-masaf-list) of the MASAF list (`mg`): they are drawn like the other monumental trees and count in "Trees in view", Completeness and Record trees. Their card has the group line and not the note for other sources, also when they have a `ref:masaf` of their own without `denotation=natural_monument`; members that already have `denotation=natural_monument` come from the query and only get the group line.

It opens from the globe icon next to "Monumental tree" in the legend. On opening the map shows Europe. Below zoom 7 only one tree per area is shown and the others appear as you zoom in: for each zoom the world is divided into 48-pixel cells and in each cell one tree is shown, chosen in this order: first those with a photo on the card, then the largest (circumference measured or from the diameter, then height; measurements reported as errors do not count), then those with a name or `wikidata`. They are about 3,000 trees out of 90,000, in a separate file of less than 200 KB, and every zoom change takes a few tenths of a second; with all the trees even at low zoom the map stayed empty for several seconds (12 s at zoom 3 over Europe). From zoom 7 all are shown. The count below zoom 7 says "zoom in to see all", and the genus and species filter shows, below zoom 7, only the trees chosen for their areas. It has only the panel with the map title, "← Back to the QA tool", the genus and species filter, the count of trees in view and the date of the data; trees do not have the red outline for errors. The legend does not have the entries that cannot appear there (with errors, landmark, stump) and, in place of "Sacred tree", has "Monumental and sacred" with the half-yellow, half-light-blue outline. On the card, in place of the errors, there is only "⚠ see in the QA tool", which opens the tree in the tool, if the tree has errors and is in a region of the tool.

From zoom 7 the map also shows the trees of the MASAF list of monumental trees of Italy that are not yet on OpenStreetMap, with a dashed golden outline, as large as an OSM monumental tree without `diameter_crown` (crown of 5 m radius at real size, minimum 3 px; 6 m if the tree is also listed for crown width, criterion a2.3: `MASAF_CROWN_R` and `MASAF_CROWN_R_WIDE` in `scripts/fetch_world.py`), with the colour and (from zoom 16) the shape of the crown derived from the species as for OSM trees: `leaf_type` and `leaf_cycle` estimated from the wiki lists ([issue #17](https://github.com/ivanbranco/tree-osm-qa/issues/17)), and (from zoom 16) the trunk as for OSM trees, from the circumference in the list or, if missing, estimated from the height (lighter), and a card of its own: the data of the list (species without authors, place, type, height, circumference, criteria), the note "not on OpenStreetMap yet", the source citation required by the licence (CC BY 4.0) and the "Open on OpenStreetMap" link, which opens openstreetmap.org at zoom 19 on that point. A tree in the list is already on OSM if a node in Italy, a way or a relation has its code in `ref:masaf` (leading zeros do not count), or if an OSM monumental tree of the same genus is within 25 m (`MASAF_NEAR` in `scripts/fetch_world.py`); the members of homogeneous groups that are monumental only for the group do not count for this distance (the code of their relation already counts). The comparison is redone at every update of the map, so a tree added on OSM disappears from the dashed ones on the next run; the list data is in `scripts/masaf_trees.json`, written by `scripts/update_masaf.py`, and the result in `data/world/masaf.geojson.gz`. The genus and species filter also applies to these trees; the "Trees in view" count counts only OSM trees.

The "Completeness" tab of this map (see [Completeness](pannello.md#completeness)) has, at the top, the counter of the trees of the MASAF list already on OSM, "X of Y" with a bar, for Italy and, under "By region", for each Italian region, from the most complete (by the percentage shown, then alphabetically). The counter appears only when the centre of the map is in Italy (inside the national boundary `g:Italia` of `data/regions_boundaries.geojson`, loaded when the tab is first opened; the boundary follows the coast, so with the centre on the sea the counter is hidden). It uses the same matching described above: `scripts/fetch_world.py` writes in `data/world/index.json` the number of listed trees (`masaf_total`), the trees not yet on OSM (`masaf`) and, for each region, `masaf_regions` (`{region slug: [already on OSM, listed]}`); the region is the last part of the MASAF code (the ISTAT code of the region; 21 and 22, the provinces of Bolzano and Trento, are counted together as Trentino-Alto Adige: `MASAF_REGIONS`). Tapping the counter highlights on the map, in magenta and at every zoom (also below zoom 7), the MASAF trees not yet on OSM; from far away they can also be clicked to open their card. With data written before these fields existed, the tab shows only how many trees are not yet on OSM, and says that the count will arrive with the next update of the map. Below the counter, the bars of the trees in view: Species, Height, Circumference and Photo, and Crown diameter apart, as optional; they count the OSM trees shown on the map (below zoom 7 only those chosen for their areas, and a note says so), including those that are monumental only according to other sources and the members of homogeneous groups, not the MASAF trees not on OSM.

The page in the folder loads `index.html` setting the mode (`window.DENDROSM_MODE`, see `MODE` in the script): the code is one. The data is in `data/world/monumental.geojson.gz` (same checks as the tool; the `qa` property is the tool's region in which the tree falls, from the boundaries of `data/regions_boundaries.geojson`; `mz` is the zoom from which the tree appears, only for those visible below zoom 7), `data/world/monumental.low.geojson.gz` (only the trees with `mz`) and `data/world/index.json`. They are updated manually from the "Update monumental map" Action (`scripts/fetch_world.py`, locally `python scripts/fetch_world.py`). The Overpass query is split into boxes: starting from the whole world, a box is divided into 4 until it holds at most 15,000 trees in the data of the previous update (`TILE_MAX`; about 20 boxes), and a box that does not answer is divided again, at most 2 more levels (`TILE_EXTRA_DEPTH`). If a box still does not answer, the previous data is kept. The boxes are computed again at every run, from the data just written. Each box asks only for the exact values `denotation=natural_monument` and `monument=tree`, and `natural=tree` is checked afterwards in the script; nodes with several values (such as `natural_monument;landmark` or `monument=tree;memorial`) come from one separate worldwide query (`multi`), and if it does not answer the update goes on without them, with a warning. Links (`image`, `website`, `url`) are not rechecked: the broken-link check uses the tool's cache.

## Height bands for the estimated trunk

When a tree has `height=*` but no `circumference=*` (or `diameter=*`), the trunk is drawn from an estimated circumference: height divided by a height/circumference ratio. The ratio is chosen in this order: the ratio of the species (`height_circ_ratio` in `scripts/species_limits.json`), then the ratio of the tree's height band, then the single general value (12). Some species have height bands of their own, or use the general bands before their single ratio: see [Height bands per species](#height-bands-per-species). A tree without a height does not use the bands. The general bands are the same for all species ([issue #39](https://github.com/ivanbranco/tree-osm-qa/issues/39)):

| Height (m) | Trees in the sample | Height/circumference ratio |
|---|---|---|
| 0–6 | 69,933 | 15.4 |
| 6–8 | 59,248 | 13.2 |
| 8–15 | 150,834 | 11.1 |
| 15–20 | 46,372 | 11.3 |
| 20–30 | 22,792 | 12.0 |
| 30 and above | 2,606 | 11.4 |

The lower bound belongs to the band (a tree of exactly 6 m is in 6–8), and the bands have no gaps.

* **Why**: with the single value, trees below 6 m were drawn with a trunk circumference 28% larger than the median of the measured ones (their median ratio is 15.4, not 12). On trees that have both measurements, the median error of the estimate (absolute difference of the logarithms of the estimated and mapped circumference) goes from 0.307 to 0.283 overall, and from 0.470 to 0.345 below 6 m; from 8 m upwards it changes by 5% at most, because there the band medians are close to 12
* **Sample**: the 351,785 trees in `data/regions` with height and circumference both mapped (circumference also from `diameter=*`; stumps excluded) and without `denotation=natural_monument`, in November 2026. Monumental trees are left out because they are 0.3% of the trees that get the band estimate, but 36% of the measured trees from 20 m upwards, where they lower the median by up to 14% (20–30 m: 10.3 with them, 12.0 without)
* **Boundaries**: 6 and 8 m follow the data: the median ratio is between 15 and 17 up to 6 m (also at exactly 5 m, a very frequent value) and reaches 11 from 8 m
* **Minimum**: a band needs at least 1,000 trees; a band with fewer is merged with a neighbouring one
* **Fixed values**: the medians were computed once and are written in `height_circ_ratio_bands` under `_default` in `scripts/species_limits.json` (rows `[minimum height, ratio]`); region updates do not recompute them
* The bands are used only to draw the trunk: the thresholds of the checks on the height/circumference ratio do not use them

### Height bands per species

For nine species the order is different ([issue #42](https://github.com/ivanbranco/tree-osm-qa/issues/42)). Four have height bands of their own, used before the single ratio of the species:

| Species | Trees in the sample | Bands: height (m), ratio, trees |
|---|---|---|
| Aesculus hippocastanum | 22,635 | 0–6: 15.4 (1,172) · 6–8: 11.5 (1,934) · 8–15: 9.3 (12,549) · 15–20: 9.0 (4,993) · 20 and above: 10.0 (1,987) |
| Carpinus betulus | 7,226 | 0–6: 19.9 (2,794) · 6–8: 16.3 (1,296) · 8–15: 14.3 (2,657) · 15 and above: 15.5 (479) |
| Gleditsia triacanthos | 3,214 | 0–8: 20.0 (1,571) · 8–15: 12.9 (1,335) · 15 and above: 13.0 (308) |
| Liriodendron tulipifera | 1,523 | 0–8: 19.1 (671) · 8 and above: 13.5 (852) |

For five species the general bands are used before the single ratio of the species: Acer platanoides, Acer pseudoplatanus, Celtis australis, Salix alba, Tilia cordata. For all the other species the order is the one described above.

Median error of the estimate (same measure as for the general bands), with the single ratio of the species, the general bands and the bands of the species. "Held-out regions" is the error of the bands of the species when they are computed without one region and measured on that region, in turn for every region:

| Species | Single ratio | General bands | Bands of the species | Bands of the species, held-out regions | Regions where they beat the general bands |
|---|---|---|---|---|---|
| Aesculus hippocastanum | 0.244 | 0.259 | 0.206 | 0.215 | 5 of 6 |
| Carpinus betulus | 0.313 | 0.360 | 0.263 | 0.290 | 6 of 6 |
| Gleditsia triacanthos | 0.250 | 0.261 | 0.197 | 0.223 | 3 of 4 |
| Liriodendron tulipifera | 0.243 | 0.273 | 0.195 | 0.209 | 5 of 5 |
| Acer platanoides | 0.276 | 0.248 | 0.239 | 0.242 | 5 of 7 |
| Acer pseudoplatanus | 0.278 | 0.230 | 0.224 | 0.246 | 1 of 6 |
| Celtis australis | 0.329 | 0.261 | 0.223 | 0.236 | 4 of 5 |
| Salix alba | 0.453 | 0.423 | 0.403 | 0.474 | 1 of 5 |
| Tilia cordata | 0.293 | 0.238 | 0.222 | 0.245 | 4 of 7 |

* **Sample and measure**: the same as for the general bands, recomputed in November 2026 (352,042 trees). The names of a group of synonyms count as one species, as in the rest of the map
* **Regions**: 7 regions hold almost all the sample (Vienna 34%, Île-de-France 23%, Grand Est 15%), and for most species one region has 40–70% of the trees. With a random split of the trees almost every species improves with bands of its own; with held-out regions many of these gains disappear (Tilia cordata: 0.222 on the whole sample, 0.245 with held-out regions, against 0.238 of the general bands). The held-out regions are the test that decides
* **Minimum per species**: 1,000 trees and 3 regions with at least 100 trees each. With fewer trees the uncertainty of the median error (0.01–0.02) is as large as the gains; with fewer regions the test cannot be done. 50 species have 1,000 trees, 39 of them in 3 regions
* **Minimum per band**: 300 trees; a band with fewer is merged with a neighbouring one. With 300 trees the uncertainty of the median of a band is about 3%, and the bands of a species differ by 10–40%
* **Boundaries**: those of the general bands. Boundaries chosen on the data of each species (successive splits at whole metres) gave a higher error with held-out regions in 8 of the 12 most numerous species, and a lower one in 3. In Gleditsia triacanthos and Liriodendron tulipifera 0–6 and 6–8 are one band: the two medians were equal in the first (20.0) and in reverse order in the second (16.7 and 20.0)
* **Bands of the species**: only if, with held-out regions, their error is lower than both the general bands and the single ratio (90% interval of the difference, from resampling the trees, entirely below zero), lower than the general bands in most regions, and lower also on the trees outside the region with the most trees. Acer platanoides meets these conditions with a difference of 0.007 from the general bands, and Celtis australis does not meet the last one (outside Vienna 0.276 against 0.261): both use the general bands
* **General bands before the single ratio**: among the 43 species with a single ratio, in 11 its error is higher than that of the general bands (90% interval entirely above zero), in 12 the two are equal within the interval, in 20 it is lower. The order changes only for the species where the general bands are better also in most regions and outside the region with the most trees. Fraxinus excelsior, Quercus robur, Corylus colurna and Fraxinus ornus do not meet these two conditions; Quercus rubra (948 trees) and Olea europaea (72) are below the minimum per species
* **Fixed values**: computed once and written in `height_circ_ratio_bands` in the entry of the species in `scripts/species_limits.json`: rows `[minimum height, ratio]` for the bands of the species, `"default"` for the general bands before the single ratio. Region updates do not recompute them
* `height_circ_ratio` of these species is unchanged: the check on the height/circumference ratio of the species and the trunk comparison window use it as before
* The trees of the MASAF list that are not on OSM (monumental trees map) get the same estimate, from the same function

## Structure

* `scripts/fetch_trees.py` – downloads from Overpass, computes the checks, writes the data
* `scripts/test_checks.py` – test cases of the checks, see [Tests of the checks](#regions-and-data)
* `scripts/fetch_world.py` – data of the world map (monumental trees of the whole world)
* `scripts/regions.json` – list of regions
* `scripts/update_boundaries.py` – downloads the region boundaries into `data/regions_boundaries.geojson` and those of the areas not covered into `data/uncovered_boundaries.geojson`
* `scripts/make_countries.py` – writes `scripts/countries.json` from Overpass results
* `scripts/update_reference_lists.py` – downloads the species and genus lists from the OSM wiki into `scripts/species_list.json` and `scripts/genus_list.json` (for genera also the common names of the `genus:xx` columns, under `names`), and the `denotation` values with the number of uses from Taginfo into `scripts/denotation_values.json`
* `scripts/species_limits.json` – per species: height and circumference limits (`height_source` / `circumference_source` when the record does not come from monumentaltrees.com, `height_url` / `circumference_url` for the page of the record at its source), ratios used to estimate missing dimensions; the entry of a name in the wiki list also applies to its synonyms in `scripts/whitelist.json` and to the other spellings of the group's names (`x` instead of `×`, for example `Platanus x acerifolia` uses `Platanus × hispanica`); under `_default`, the general ratios and the height bands (`height_circ_ratio_bands`, see [Height bands for the estimated trunk](#height-bands-for-the-estimated-trunk)); `height_circ_ratio_bands` in the entry of a species gives its own bands, or `"default"` (see [Height bands per species](#height-bands-per-species))
* `scripts/update_masaf.py` – from the KML file of the MASAF list of monumental trees of Italy (downloaded manually from the [list page](https://www.masaf.gov.it/flex/cm/pages/ServeBLOB.php/L/IT/IDPagina/11260); about 30 MB, it does not go in the repository) writes `scripts/masaf_list.json`: each code with its status, listed or removed (reason and decree), for the check on removed trees; and `scripts/masaf_trees.json`, the listed trees with position, species, place, measurements and criteria, for the monumental trees map. It is rerun manually when a new version of the list comes out: `python scripts/update_masaf.py "Alberi monumentali d'Italia.kml"`. The loaded version is at the top of `scripts/masaf_list.json` (`"version"`, read from the KML description: currently "X Aggiornamento, D.Dir. n. 364243 del 24/07/2026"); if a new KML has the same version, the script says so
* `scripts/year_events.json` – sentences about the year for the Oldest record of the Record trees tab, see above
* `scripts/masaf_thresholds.json` – the MASAF indicative minimum circumferences per species (January 2020 table, from the PDF of [issue #1](https://github.com/ivanbranco/tree-osm-qa/issues/1)), transcribed by hand, for the hint on Italian trees that reach the threshold. The PDF does not go in the repository
* `scripts/whitelist.json` – exceptions to the checks: `species:wikidata` accepted per species (`wikidata_mismatch`), species not to be reported as misspelled (`species_typo`) and synonyms (`synonyms`: alternative name → name in the wiki list, for example `Crataegus × lavallei` → `Crataegus × lavalleei`; the alternative name counts as the one in the list in all checks, and the `species:wikidata` accepted for any name of the group are accepted for all of them, so that no tree is asked to change its name or its QID to the synonym's; the map counts and filters the trees of a group as one species, under the name in the wiki list, for example `Platanus × acerifolia`, `Platanus acerifolia` and `Platanus hispanica` under `Platanus × hispanica`; `species` itself is never changed) and monumental trees that really are very small (`small_monument`: node id → note)
* `.github/workflows/update.yml` – data update (runs the tests of the checks first)
* `.github/workflows/test-checks.yml` – "Test checks" Action: the tests of the checks, at every push that changes `scripts/`
* `.github/workflows/update-boundaries.yml` – boundaries update (manual only)
* `.github/workflows/update-species-list.yml` – "Update reference lists" Action: species, genera and `denotation` values (manual only)
* `.github/workflows/update-world.yml` – "Update monumental map" Action (manual only)
* `everydoor/build_plugin.py` – builds the [Every Door plugin](everydoor.md) `everydoor/dendrosm.edp` from the reference lists; `everydoor/fetch_names.py` downloads the common names of the species from Wikidata into `everydoor/names.json`; `everydoor/version.json` holds the plugin version, raised by the build when the content changes
* `index.html` – the site
* `i18n/<code>.js` – the texts of the languages translated by volunteers (`i18n/fr.js`), loaded only for that language; `i18n/<code>-missing.md` – the texts still to translate, written by `scripts/i18n_missing.py` ([Translating DendrOSM](translating.md))
* `monumental-trees/index.html` – the world map of monumental trees (loads `index.html`); `monumental-trees/favicon.svg` and `favicon.png` are its icon, the same as the tool's but golden
* `taginfo.json` – the OSM tags used by the project, in the [Taginfo format](https://wiki.openstreetmap.org/wiki/Taginfo/Projects); if a tag is added or removed in `fetch_trees.py`, it must be updated here too

To publish, enable GitHub Pages from the `main` branch, root folder.
